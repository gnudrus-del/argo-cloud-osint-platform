## [Unreleased]

- **Fix: the 8 lower-severity findings from the same audit** (previously documented here as a deferred backlog — now closed, same rigor: patch + regression test + full suite + live verification where observable):
  - `policy.py::_target_in_scope` didn't handle CIDR (`10.0.0.0/24`) or wildcard (`*.example.com`) scope entries at all — a `/` in an entry excluded it from every match branch, and a `*.` prefix was compared literally. A case scoped to a whole authorised network denied every IP inside it. Now handled via real `ipaddress` containment (IPv4 and IPv6) and by treating `*.domain` as the existing apex+subtree domain match. 5 new tests.
  - `ConnectorSweepAgent` (`agents.py`) swallowed the connector name and exception detail when a connector raised before producing a `ConnectorResult`, and reported `status="skipped"` even when *every* connector failed — the same label used for "0 connectors applicable here", a benign case. Now logs which connector(s) failed, records them in the agent's notes, and reports `status="error"` when there were failures and zero successes. 1 new test.
  - `execute_job` (`web.py`) called `read_job(job_id)` before its own `try` — combined with the `job_queue.py` fix above, a job deleted while still queued (`handle_job_delete` allows deleting a job in any status) no longer kills the worker, but that specific job vanished with no trace in storage. Now guarded with a `job = None` sentinel so the `except` can record a `job_error` audit event instead of risking a `NameError` on an unbound `job`. 1 new test.
  - Three connectors (`maigret`, `toutatis`) plus the already-partially-documented `misp_client` are labelled "key-free" in `docs/CONNECTORS.md` alongside genuinely zero-setup connectors, but actually require one-time *server* configuration (`MAIGRET_PYTHON`/`MAIGRET_CMD`, `TOUTATIS_SESSION`) before they produce anything — documentation now calls this out explicitly, distinct from the true zero-setup entries (`sherlock_lite`, `gdelt`, `wikipedia_search`). UI-side distinction (a third "needs server setup" category in the coverage panel, beyond key-free/BYOK) not done in this pass.
  - `app.js::pollCombinedJobs` used a single shared `state.combinedPollTimer` slot: starting a second search before the first finished polling silently cancelled the first one's interval — its job kept running server-side but its results never appeared. Each call now owns its own local timer; concurrent searches no longer stomp each other. Same function also treated any polling error (a transient network blip included) as "job complete"; now only a genuine 404 (job actually deleted) removes it from the pending set, anything else is retried on the next tick.
  - `app.js::showEntityProfile` re-attached a `click` listener on every `.entityTab` button via `addEventListener` on every profile open, on static markup that's never recreated — listeners accumulated for the rest of the session (no wrong data produced, since the last-attached handler always won, but growing redundant work). Switched to `.onclick =` assignment, which always replaces rather than stacks.
  - `i18n.js`'s language switch only re-translated static `[data-i18n]` nodes; the entity profile, jobs/cases lists, dashboard and API-keys panel — all built via `innerHTML` with `t()` resolved once at render time — stayed in the previous language until the user happened to re-trigger that specific view. The `i18n:changed` listener now re-invokes whichever panel loader matches the currently active panel, and re-renders the entity profile directly if one is open.

  1162 passed, 4 skipped, 21 subtests after this batch (up from 1155); `ruff check` and the SSRF guard both clean. The 4 frontend fixes (poll timer independence, 404-vs-transient-error handling, no listener accumulation, i18n re-render dispatch) were each verified live against a running local instance via direct, targeted JS execution — not just unit tests — confirming the exact before/after behaviour change for each.

- **Fix: name/username searches — the product's core use case — silently ran on the wrong target_type, plus 5 more bugs found in a full-codebase audit triggered by the fix above.** `infer_target_type()` (`osint_bot/orchestrator.py`), the classifier actually wired into the pipeline, defaulted any plain text with no Italian magic word ("persona"/"socmint"/"username"/"handle") to `"company"` — so a bare `"Mario Rossi"` never reached the person/handle connector toolchain (`sherlock_lite`, `maigret`, `toutatis`, `darkweb_scan`, ...). Worse, the dashboard's main search bar (`routeGlobalSearch` in `app.js`) and the CLI without `--type` (`cli.py`) both fed exactly that path, so the two most visible entry points to the product silently misrouted every plain-name search. Fixed by deferring to the already-tested `target_classifier.classify_target()` as the fallback instead of hardcoding `"company"`, and by giving `app.js`/`cli.py` the same "auto-detect if unset" treatment `--command` mode already had. 6 new tests (`tests/test_orchestrator.py::InferTargetTypeFallbackTests`), verified live in a running instance (browser JS execution, not just unit tests).
  - `holehe.py`'s stdout parser (`_HIT_RE`) was anchored to end-of-line, so any hit with extra data appended by holehe itself (recovery email, phone, **FullName** — exactly the highest-value person-search signal, exposed by gravatar/protonmail/odnoklassniki) was dropped *entirely*, not just the extra data. Now the base hit always survives, and FullName is extracted into a new `person_name_hint` finding. 2 new regression tests, verified against the actual installed holehe package's output format (`core.py::print_result`), not assumed.
  - `check_policy()` (`osint_bot/policy.py`, the gate every native connector goes through) never checked the RoE's time window or its four-eyes/second-signature requirement — both are enforced correctly for external tools via `safety.authorize_action`, but silently skipped for all 63+ native connectors. An expired-but-not-revoked RoE kept authorising gated connectors past its mandate; a RoE requiring co-signature let active/darkweb-gated connectors run without one. 6 new regression tests (`tests/test_policy_gate.py::RoeWindowAndFourEyesTests`).
  - `JobQueue._run()` (`osint_bot/job_queue.py`) had no `except` around the job handler — an unhandled exception (e.g. `execute_job`'s `read_job()` on a job deleted while still queued, which `handle_job_delete` allows) killed the daemon worker thread, silently stranding every job already queued behind it until an unrelated new job happened to spawn a replacement worker. Now caught and logged; the worker survives. 1 new regression test.
  - `GET /api/cases/<id>/profile.json` (`build_case_profile`, extracted from `handle_case_profile` into a plain testable function) 404'd when 0 jobs had completed, and even when jobs *did* complete, never included `agent_results` — so a fresh install with unconfigured BYOK keys showed "0 evidenze" on the aggregate case view, indistinguishable from "nothing exists online about this person." Now always 200s with `job_status_summary`/`failed_jobs`/`agent_results`, and the frontend (`renderEntityOverview`, `renderAuditTab`) surfaces *why* (e.g. "1 queued — cached=1,error=2,missing_key=5,ok=5,policy_denied=1") instead of a bare "no evidence" message. 4 new backend tests.
  - `renderEvidencesTab` (`app.js`) truncated findings to 50 with no indication, and since the connector-sweep agent (the ~60-connector differentiator) is always merged last, its findings were structurally the first ones cut whenever other agents already produced 50+. Now all findings render — the overflow past 50 is in a collapsible `<details>` section (same pattern already used by the AI triage tab), never silently dropped from the DOM.
  - Full audit method: 3 parallel deep-dive passes (person-search connector coverage, backend correctness sweep for the same "declares X, does Y" bug family, frontend rendering correctness), each independently sourced with file:line evidence, then verified by hand before any fix — not applied on the audit's word alone.

- **Fix: repeat searches silently returned stale/incomplete results instead of fresh findings** — two independent bugs, both found while diagnosing a "the site never finds new information, it just re-shows what it already has" report against the live deployment:
  1. `BaseConnector`'s per-connector cache (`osint_bot/connector.py`) is a process-lifetime singleton keyed only by `connector+target+target_type` (no `case_id`/`job_id`/actor), with TTLs up to 86400s/24h declared by ~19 connectors (`maigret`, `hunter`, `securitytrails`, `linkedin2username`, `wayback`, `gravatar`, `rdap`, `ipinfo`, `sec_edgar`, `opencorporates`, `companies_house`, `nominatim`, `overpass`, `phone_footprint`, `wikipedia_search`, `dnstwist_native`, `asn_lookup`, `contactout`, `lusha`). A cache hit comes back with `status="cached"` but is treated identically to a fresh `"ok"` result by `ConnectorSweepAgent`, and the report never surfaced `cached`/`provenance.collected_at` — so re-searching the same target within hours (up to a day, for those connectors) silently served the exact same findings, presented as freshly collected. Fixed with a hard `MAX_EFFECTIVE_CACHE_TTL = 120` ceiling applied inside `BaseConnector.run()`: every connector's declared `cache_ttl` is now clamped to at most 2 minutes at request time — long enough to absorb an accidental double-submit/page-reload, short enough that any deliberate re-run gets a live fetch. Each connector's own declared `cache_ttl` is untouched (introspection/docs still show the original value); only what's actually honoured at read time changed. New regression test `test_long_declared_ttl_is_capped_to_effective_ceiling` (`tests/test_connectors.py`).
  2. `ensure_default_case()` (`osint_bot/web.py`) — the case every job uses unless the caller explicitly picks one — never populated `allowed_targets`, neither on creation nor on later reuse. `policy.py`'s gated-connector check refuses any PII/active/darkweb-gated connector against an empty scope regardless of the case's RoE, which *was* already correctly permissive (`allowed_classes: ["passive", "active-gated", "pii-gated", "darkweb-gated"]`, auto-signed by `_auto_sign_permissive_roe`). Net effect: `contactout`, `lusha`, `hibp`, `hunter`, `emailrep`, `cloud_buckets`, `content_discovery`, `port_scan`, `darkweb_scan` — 9 of the highest-signal connectors — were `policy_denied` on **every** standard-UI search, silently, regardless of the "confirm_authorization" checkbox the user ticked (recorded in the audit trail but never actually wired to the scope gate that would let those connectors run). Fixed: `ensure_default_case(actor, target=..., authorized=...)` now additively and idempotently adds the confirmed target to the case's scope when the caller has ticked authorization for it; `create_job` passes the job's actual target and `confirm_authorization` flag through. Scope grows across searches on the same default case, never shrinks, and an unconfirmed/different target stays out of scope. 4 new regression tests (`tests/test_policy_gate.py::DefaultCaseAutoScopeTests`).

  Full suite green (1136 passed, 4 skipped, 21 subtests) after both fixes; `ruff check` clean. Not yet deployed to the live instance — needs a `git pull` + service restart on the server to take effect.
- **Every native connector now runs on every search, together — not a curated subset**: the 63 connectors in `connectors/` (crt.sh, Shodan, HIBP, holehe, maigret, etc.) were previously reachable ONLY through the manual single-connector UI panel (`POST /api/connectors/run`) — the automated "Cerca" pipeline that produces reports never touched them. New `ConnectorSweepAgent` (in `ALWAYS_ON_AGENTS`) runs every connector whose `input_types` match the search target, in parallel (thread pool), on every job. Safety is unchanged: `BaseConnector.run()`'s existing RoE/case-scope policy gate still applies per-call, and the agent additionally pre-filters gated action classes on the same opt-in flags already used elsewhere in the pipeline (`allow_darkweb`, `allow_network_scan`, `include_contact`) — a plain search never silently reaches for active/PII/darkweb connectors. Also broadened `choose_external_tools` (CLI tool auto-selection) to fire whenever the target type + `confirm_authorization` match, instead of requiring a keyword like "auto"/"tool" in the search text or an explicitly ticked module — the previous behavior meant most ordinary searches ("analizza questo dominio") never triggered *any* auto-selected external tool. Real bugs found and fixed while diagnosing this against the live deployment: the "Enable AI enrichment" case toggle failed completely silently on a disabled server (a deliberate 404 kill-switch, `OSINT_AI_AGENTS_ENABLED`, now surfaced with a real on-screen message instead of an invisible tooltip); the entity graph's node layout ignored `relationships` entirely (nodes placed purely by array index, producing an unreadable hairball) — replaced with a real force-directed spring-embedder (pure JS, no external library). 8 new offline tests for `ConnectorSweepAgent` (`test_connector_sweep_agent.py`).
- **Three new key-free native connectors** (63 → 66; 46 → 49 key-free): `ripe_stat` (RIPEstat — network prefix/ASN/abuse-contact for an IP, RIPE NCC's free public API), `hackertarget` (reverse-IP lookup — other domains hosted on the same IP, infrastructure correlation), `wikipedia_search` (public background context for a company/person, IT-first with an EN fallback). All three offline-tested (14 new tests, `test_connectors_no_key_batch2.py`), SSRF-guard clean.
- **In-platform Methodology panel**: the confidence-tier / Admiralty-grade / severity discipline documented in `docs/METHODOLOGY.md` is now also surfaced as a sidebar panel inside the running app ("Metodologia"), not just a repo doc.
- **Admin approval gate for profile deletions (GDPR art. 17)**: a user's erasure request is no longer executed self-service on the spot. `POST /api/privacy/erase` now records a **pending** request and returns; the real atomic deletion (redaction + tombstone + row removal via the unchanged `Storage.erase_actor_data`) runs only when an admin approves it. New admin-only surface (gated by `session_is_admin`, CSRF-protected): `GET /api/admin/privacy/pending` (list of awaiting-approval erasures across all users, with owner), `POST /api/admin/privacy/approve` (executes the deletion for the request's owner — and only that owner, since a user can only ever request their own erasure), `POST /api/admin/privacy/reject` (marks it rejected, no data touched). Every step is written to the SHA-256 audit chain (`privacy_erase_requested`/`approved`/`rejected`), and the admin panel gained a "pending profile deletions" table with Approve/Reject controls. New `privacy_requests.resolved_by` column (SQLite self-migration + Postgres `ADD COLUMN IF NOT EXISTS`). Existing DSAR erasure tests retargeted through the approval path; 12 new offline unit tests (`test_privacy_erase_approval.py`).
- **RBAC — persistent per-account admin role** (roadmap item, no longer "conditional"): `users.role` (`analyst` default, `admin`), checked by a new `session_is_admin()` alongside the existing per-session unlock (`ARGO_ADMIN_USER`/`ARGO_ADMIN_PASSWORD_HASH`, unchanged, still works exactly as before as a break-glass path). Role assignment is a new local CLI command, `argo-set-role <username> <admin|analyst> [--yes]`, **not a web endpoint** — granting admin requires shell access to the host, the same trust boundary as generating the admin password hash; there is no "an admin can promote other users over the web" surface by design. Takes effect on the account's very next request (role is read from storage per-request, not cached in the session). SQLite migration + Postgres `ADD COLUMN IF NOT EXISTS`, both backward-compatible; `public_user()` now exposes `role` to the frontend (informational — the server-side gate never trusts a client-supplied role). 18 new offline unit tests (`test_rbac.py`, `test_cli_set_role.py`).
- **`web-next/` CSRF + Docker wiring** (issue `#H4`, partial — track A of two): the experimental Next.js console gained CSRF token exchange (`lib/session.ts` fetches the token from `GET /api/auth/status` since this console has no login of its own, `lib/api.ts` attaches `X-CSRF-Token` on every state-changing request, matching `require_auth()`'s server-side check) and Docker wiring (`web-next/Dockerfile`, an opt-in `web-next` service in `docker-compose.yml` gated behind a Compose profile so `docker compose up` behavior is unchanged, a Docker smoke-build CI step). Still not promoted to the production frontend and still has no e2e tests — the `#H4` complete-vs-delete decision stays open, this only fixed the two concretely-documented gaps.
- **`docs/METHODOLOGY.md`** — writes down the confidence/source-reliability/severity discipline the `Finding` model already half-enforced in code (`confidence` float, Admiralty/NATO `source_reliability`+`info_credibility`, `severity` anchors, `why_linked`/`gaps` for auditable attribution) but never documented as a single citable convention. Linked from `README.md`, `CONNECTORS.md`, and `CONTRIBUTING_MODULES.md`. No code behavior change — pure documentation, adapted from general OSINT-methodology practice to Argo's actual authorized-case context (not external red-team).
- **Google Sign-In** (`GOOGLE_OAUTH_CLIENT_ID`, optional `auth` extra: `google-auth` + `requests`) — an additional login door alongside the existing email+password signup/login, not a replacement. Server-side ID token verification (signature, issuer, audience, `email_verified`) via `osint_bot/google_auth.py`; first-time sign-in auto-provisions a user (already verified, no usable password — password login stays impossible for that account by construction, `verify_password` fails closed on an empty hash). New `users.auth_provider`/`users.google_sub` columns (SQLite migration + Postgres `ADD COLUMN IF NOT EXISTS`, both backward-compatible). Admin metrics (`/api/admin/stats`, behind the existing admin unlock) gained a per-user login history table (username, email, method, login count, last login) built from the existing audit chain — no new tracking table. 22 new offline unit tests (`test_google_auth.py`, `test_admin_login_history.py`).
- **Two new BYOK connectors** (61 → 63 native connectors, 15 → 17 BYOK): `contactout` and `lusha` (LinkedIn profile URL or email → personal/professional email + phone, PII-gated). Both wired into `API_KEY_CATALOG` (`CONTACTOUT_API_KEY`, `LUSHA_API_KEY`), with 24 offline unit tests covering missing-key, invalid-target, auth/quota, rate-limit, and defensive response-shape extraction (the upstream JSON schemas are not stably documented across plans, so extraction tries multiple known field paths, same pattern as `influencers_club.py`). Deliberately does **not** include automated login/session-based scraping of Facebook/Instagram/LinkedIn/TikTok — that would violate each platform's Terms of Service and Argo's own stated no-automated-exploitation / no-mass-surveillance scope (`docs/FAQ.md`); existing passive coverage for those platforms (`toutatis`, `linkedin2username`, `socid_extractor`, `ghunt`) is unchanged.
- **Three new key-free connectors** (58 → 61 native connectors, 43 → 46 key-free): `cloud_buckets` (S3/GCS/Azure bucket permutation — active, RoE-gated, flags listable/exposed storage), `email_security` (SPF/DMARC/MTA-STS/DNSSEC posture — passive, flags spoofable domains), `hudsonrock` (Hudson Rock Cavalier infostealer breach-corpus lookup by domain/email — passive, free public API, no key). All three ship with offline unit tests and pass the SSRF guard.
- **CLI RoE/scope gate** (`argo-osint --case-id <id>`): the CLI's external-tool execution path can now go through the same case-based RoE/scope authorization as the web UI, not just its own lighter consent-flag gate. The plumbing (`case_id`/`actor` threaded through `AgentContext` → `PluginContext` → `run_tool` → `authorize_action`) already existed; what was missing was the `--case-id`/`--actor` CLI flags themselves and a working storage lookup — `osint_bot.plugins._lazy_storage()` read the raw `web.STORAGE` global (always `None` in a standalone CLI process, since nothing had called `web.get_storage()` to initialize it) instead of the lazy-initializing `web.get_storage()`. Without `--case-id`, CLI behavior is unchanged (the historical consent-flag gate).
- Report sealing: Ed25519 signature on every completed job (always on) + optional on-demand RFC3161 trusted timestamping (`report_signing.py`, `tsa_client.py`), CLI `argo-verify-report`.
- Privacy Center / DSAR made backend-portable: erasure, export and audit-redaction logic moved off raw SQLite SQL onto the shared `Storage`/`PostgresStorage` interface, so it now works correctly (not silently as a zero-column no-op) on Postgres.
- Postgres positioned as the recommended backend for production/multi-analyst deployments: wired into `docker-compose.yml`, `OSINT_STORAGE_STRICT` flag for a loud failure instead of a silent SQLite fallback, exercised in CI against a real `postgres:16` container. SQLite remains the zero-config default.
- `docs/AUDIT_READINESS.md` — preparatory material (suggested scope, dependencies, active CI gates) for a paid third-party security review. Not itself an audit.
- `pip-audit` dependency-scan CI job; `Pillow` bumped to `>=12.3.0` (5 known CVEs fixed).
- AI agent integration (opt-in, `ai` extra): narrative report synthesis, entity-resolution suggestions, finding triage via a BYOK LLM provider (Anthropic / OpenAI / local OpenAI-compatible endpoint), gated by a server kill switch + per-case consent + per-analyst key.
- **BYOK API key encryption at rest** (`osint_bot/secrets_crypto.py`): envelope encryption (AES-256-GCM, a random per-secret data key wrapped by an instance master key), row-bound via AES-GCM associated data (`enc:v2:`, with transparent read-compat for the earlier unbound `enc:v1:` format and for pre-existing legacy plaintext), the master key held outside the database (env var, systemd-credential file, or an auto-generated local file — never a DB row, never in `.env`), per-access audit events (`api_key_stored` / `api_key_accessed` / `api_key_deleted`), and an `argo-rotate-master-key` CLI for rotation. Values are never written to logs, backups, or DSAR exports (the export path already selected only `service`/`created_at`, never `value`).
- **Ed25519 report-signing key rotation** (`report_signing.rotate_signing_key`, CLI `argo-rotate-signing-key`): retires and archives the current key, generates a new one; past signatures stay verifiable unchanged since every seal embeds its own public key.
- **Internal adversarial security review** of the above (envelope encryption, both rotation CLIs), performed independently of the code that was reviewed. Found and fixed: a rotation-ordering bug in `argo-rotate-master-key` that could have permanently lost API keys on a crash mid-rotation; a false "no restart needed" claim in `argo-rotate-signing-key`'s output; a low-probability archive-filename collision under concurrent signing-key rotation; missing row-binding on stored ciphertext (the AAD change above); and silently-swallowed file-permission failures (now logged). Documented as internal due diligence, explicitly not a substitute for an external audit — see `docs/AUDIT_READINESS.md`.
- Documentation fact-check pass across `README.md`, `SECURITY.md`, `docs/*` correcting stale/aspirational claims (connector counts, "tamper-evident" scope, encryption-at-rest status).

## [0.2.0] — 2026-07-14

### Added

- **Bilingual UI and connector output (Italian / English)** end-to-end — frontend, 59-connector-surface backend messages, per-request `ConnectorContext.lang`.
- **Centralised policy gate** — Rules of Engagement + case-scope enforcement consolidated in `BaseConnector.run` (hardening H1).

- **Real DSAR (GDPR Art. 17)** — erasure endpoint became an atomic transaction: redact audit events, append a hash-chained `dsar_tombstoned` proof, delete business rows, all in one commit (hardening H3).

- **PyPI publish workflow** scaffolded (Trusted Publisher via OIDC) — not yet triggered; the package is not live on PyPI as of this release.
- Architecture diagram replaced with a full connector map; UI screenshots and a sample forensic report added to the repo.
- `web-next/` dependency and CI maintenance (Next.js upgraded past known CVEs); marked frozen/experimental, superseded by the production Python-served UI.

### Known limitations (carried forward)

- BYOK provider keys still stored plaintext in `.env` — encryption-at-rest remains planned, not yet built. *(Resolved in Unreleased above.)*
- No PyPI package published yet (workflow exists, unused).
- Datastore not encrypted at rest — relies on OS-level disk encryption.
